HidroSSO

Principio fundamental

El usuario se autentica una sola vez en hidrosso.hidrobart.com con su cuenta Microsoft 365. A partir de ahí accede a cualquier app Hidrobart sin volver a ingresar credenciales. Las apps no manejan autenticación propia — solo validan la cookie hidrosso_sid.

Arquitectura de roles

OrgRoles (grupos Azure AD) → FunctionalRoles (base de datos) → ProcessRoles (permisos por módulo)

Los roles se leen en el momento del login vía Microsoft Graph y se almacenan en la sesión de Redis. TTL de caché: 15 minutos.

Flujo SSO

De clic en el dashboard a acceso en la app destino

1
Usuario en HidroSSO dashboardHace clic en una app (ej. Costeo360)
2
HidroSSO Frontend — GET /api/sso-launch?app=costeo360Lee el hidrobartSessionId del JWT de NextAuth (server-side)
3
HidroSSO Backend — POST /auth/sso-launchCrea launch token lt_xxxx en Redis (TTL 60s, one-time). Devuelve redirect URL.
4
Browser → https://costeo360.hidrobart.com/auth/sso?lt=lt_xxxxLa página /auth/sso redirige a /api/sso-entry
5
Costeo360 — GET /api/sso-entry?lt=lt_xxxxLlama server-side a HidroSSO /auth/sso-exchange, recibe session_id, setea cookie hidrosso_sid
✓
Redirect → /dashboard de Costeo360Usuario autenticado sin haber ingresado credenciales en la app
⏱️
El launch token tiene 60 segundos de vida. Si el usuario tarda más en completar el redirect (red lenta, pestaña en background), recibirá token_expirado y deberá volver a hacer clic desde el dashboard.

Nota operativa — Error MOVED

⚠️
Azure Cache for Redis redistribuye internamente slots del cluster. El cliente Python se conecta en modo standalone al endpoint principal de Azure. Si aparece un error MOVED en el DELETE del launch token, se captura silenciosamente — el token expira en 60s de forma natural. No afecta el flujo de autenticación.
🚫
No usar RedisCluster con Azure. Los nodos internos del cluster (IPs como 52.237.x.x:8500) no son accesibles desde la VM. Si se configura RedisCluster, Redis falla completamente al iniciar y ninguna sesión puede crearse.

middleware.ts

import { NextRequest, NextResponse } from "next/server";

const PUBLIC_PATHS = ["/login", "/auth/sso", "/api/sso-entry", "/_next", "/favicon.ico"];

export function middleware(req: NextRequest) {
  const { pathname } = req.nextUrl;
  const isPublic = PUBLIC_PATHS.some((p) => pathname.startsWith(p));
  if (isPublic) return NextResponse.next();

  const sessionId = req.cookies.get("hidrosso_sid")?.value;
  if (!sessionId) {
    const hidrossoUrl = process.env.NEXT_PUBLIC_HIDROSSO_URL ?? "https://hidrosso.hidrobart.com";
    return NextResponse.redirect(hidrossoUrl);
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|images|icons|fonts).*)"],
};

app/api/sso-entry/route.ts

import { NextRequest, NextResponse } from "next/server";

const HIDROSSO_API = process.env.HIDROSSO_API_URL ?? "https://auth-api.hidrobart.com";
const POST_LOGIN_REDIRECT = "/dashboard";
const COOKIE_MAX_AGE = 60 * 60 * 8;

export async function GET(req: NextRequest) {
  const lt = req.nextUrl.searchParams.get("lt");
  if (!lt || !lt.startsWith("lt_")) return redirectToLogin(req, "token_invalido");

  let sessionId: string;
  try {
    const res = await fetch(
      `${HIDROSSO_API}/auth/sso-exchange?lt=${encodeURIComponent(lt)}`,
      { method: "GET", signal: AbortSignal.timeout(5_000) }
    );
    if (!res.ok) {
      const detail = await res.json().then((d) => d?.detail ?? "error").catch(() => "error");
      return redirectToLogin(req, res.status === 401 ? "token_expirado" : "sso_error");
    }
    const data = await res.json();
    sessionId = data.session_id;
    if (!sessionId) return redirectToLogin(req, "sso_error");
  } catch {
    return redirectToLogin(req, "hidrosso_no_disponible");
  }

  const response = NextResponse.redirect(new URL(POST_LOGIN_REDIRECT, req.nextUrl.origin));
  response.cookies.set("hidrosso_sid", sessionId, {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    path: "/",
    maxAge: COOKIE_MAX_AGE,
  });
  return response;
}

function redirectToLogin(req: NextRequest, error: string) {
  const url = new URL("/login", req.nextUrl.origin);
  url.searchParams.set("error", error);
  return NextResponse.redirect(url);
}

Leer sesión del usuario

Cómo obtener nombre, email y roles en tu app

// lib/session.ts
export async function getHidroSession(sid: string) {
  const res = await fetch(
    `${process.env.HIDROSSO_API_URL}/auth/session-info?sid=${sid}`,
    { signal: AbortSignal.timeout(3_000) }
  );
  if (!res.ok) return null;
  return res.json();
}

// En un Server Component:
import { cookies } from "next/headers";
import { getHidroSession } from "@/lib/session";
import { redirect } from "next/navigation";

const sid = cookies().get("hidrosso_sid")?.value;
const session = sid ? await getHidroSession(sid) : null;
if (!session) redirect("/login?error=sso_error");

const { name, email, roles, job_title, department } = session;

Postmortem — 2026-04-27

SSO caído en todas las apps · Duración ~45 minutos

Síntoma

Al hacer clic en Costeo360 (y otras apps) desde el dashboard de HidroSSO, el browser mostraba /login?error=sso_error. El dashboard seguía accesible pero el lanzamiento SSO fallaba consistentemente.

Causa raíz

Azure Cache for Redis redistribuyó el slot 6300 a un nodo interno diferente (52.237.54.82:8500). El cliente Python (redis.asyncio.Redis) estaba configurado en modo standalone: conecta a un único endpoint y no sabe seguir redirects MOVED.

El endpoint /auth/sso-exchange:

  1. Llama GET key → funciona (la réplica local del slot sirve lecturas)
  2. Llama DELETE key → Redis responde MOVED (escritura necesita el nodo primario del slot)
  3. El cliente lanza ResponseError → FastAPI devuelve 500
  4. Costeo360 interpreta 500 como sso_error y bloquea el acceso

Cronología

11:05
Commit de hidropluspro

Se registra HidroPlus Pro en ALLOWED_APPS y apps.json. El commit reformatea sso_router.py completo — código correcto, no introduce el bug.

~11:10
Azure redistribuye slot 6300

Azure mueve el slot de Redis a un nodo interno diferente (probable mantenimiento o rebalanceo automático).

~11:15
SSO empieza a fallar

Todos los sso-exchange devuelven 500. Los logs muestran MOVED 6300 en hidrosso-api-error.log.

~11:40
Fix desplegado

Se captura la excepción MOVED en el DELETE del launch token. El token expira en 60s. El flujo SSO vuelve a funcionar correctamente.

Qué no hacer

🚫
No usar RedisCluster con Azure Cache for Redis. Los nodos internos no son accesibles desde la VM. Al configurarlo, Redis falla completamente al iniciar — peor que el error original.

Qué vigilar

Si los logs de hidrosso-api muestran errores MOVED en operaciones distintas al delete del launch token (ms-login, session-info, etc.), significa que Azure rebalanceó varios slots. En ese caso revisar el tier de Redis en Azure Portal o considerar migrar a un tier sin clustering (Basic/Standard).

🚫
Nunca editar archivos directamente en el servidor. Editar en la VM rompe la sincronización con git: el próximo git pull puede sobreescribir los cambios o generar conflictos. En abril 2026 una edición directa causó un syntax error en el dashboard que requirió git checkout para revertir.
